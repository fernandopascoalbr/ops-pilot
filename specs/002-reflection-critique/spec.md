# Feature Specification: Reflection Critique

**Feature Branch**: `[002-reflection-critique]`

**Created**: 2026-11-04

**Status**: Draft

**Input**: User description: "Camada Reflection: withReflection(strategy, ops) decora qualquer ReasoningStrategy: executa a base; um critico (mesmo modelo, saida estruturada {approved, feedback}) avalia a resposta contra as observações do trace; se reprovar, regenera com o feedback no contexto; para em approved ou maxReflections (default 2). Evento "critique" no trace; métricas somam as chamadas extras. Arena: reflect:react e reflect:plan-and-execute"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Reflective decision-making for reactive tasks (Priority: P1)

When a reasoning strategy produces an answer for a live operational request, the system adds a reflection pass so the answer is reviewed against the evidence seen in the trace before it is treated as final. This helps catch weak reasoning, missing evidence, or unsupported conclusions before the result is shared with a user or automation.

**Why this priority**: Reactive work is often time-sensitive and high-impact, so a robust quality check is needed before acting on decisions generated by the system.

**Independent Test**: A single reactive task can be executed end-to-end and validated through a final result that includes either approval or a regenerated answer with explicit critique feedback.

**Acceptance Scenarios**:

1. **Given** a reactive reasoning task with a candidate answer, **When** the reflection layer evaluates it against trace observations, **Then** the system records a critique event and either approves the answer or requests a revision.
2. **Given** a candidate answer that does not match the available evidence, **When** the critic rejects it, **Then** the system regenerates the response using the critique feedback and keeps the revised context visible in the trace.

---

### User Story 2 - Reflective quality control for multi-step execution plans (Priority: P2)

When the system handles a plan-and-execute workflow, it must apply the same reflection pattern to the final reasoning generated for multi-step goals. This ensures the orchestrated plan is checked against the evidence, not just the immediate task outcome.

**Why this priority**: Multi-step work is more vulnerable to compounding mistakes; a reflective review reduces the chance that a plan is accepted without sufficient evidence or alignment to the trace.

**Independent Test**: A plan-and-execute scenario can be tested by creating a goal, generating a plan, and confirming that the reflection layer either approves it or produces a revised plan with critique-driven adjustments.

**Acceptance Scenarios**:

1. **Given** a plan-and-execute reasoning flow, **When** the reflection layer reviews the proposed plan, **Then** it checks the plan against trace observations before allowing the outcome to be treated as final.
2. **Given** a plan that is not sufficiently justified, **When** the critic rejects it, **Then** the system revises the plan using the critique feedback and stops once the plan is approved or the reflection limit is reached.

---

### Edge Cases

- What happens when the critic approves the first answer immediately?
- How does the system behave when the reflection loop reaches the maximum allowed attempts without approval?
- What happens if the trace contains incomplete or contradictory observations during the critique pass?
- How does the platform display or summarize the extra evaluation work in operational metrics?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST support a reflection layer that can wrap any reasoning strategy without changing the base strategy's purpose or output contract.
- **FR-002**: The reflection layer MUST execute the base strategy to produce an initial response before the critique phase begins.
- **FR-003**: The system MUST provide a critical reviewer that evaluates the generated response against trace observations and produces a structured result with approval status and feedback.
- **FR-004**: When the critic rejects a response, the system MUST regenerate the reasoning using the feedback in context so the revised answer addresses the identified gaps.
- **FR-005**: The reflection loop MUST stop once the response is approved or when the configured maximum number of reflection attempts is reached.
- **FR-006**: The system MUST emit a "critique" event in the trace for each evaluation so decision quality remains auditable.
- **FR-007**: The system MUST record the additional reasoning and evaluation work in metrics so the overhead of reflection is visible and measurable.
- **FR-008**: The reflection capability MUST be available in both reactive reasoning flows and plan-and-execute orchestration flows.
- **FR-009**: The critic MUST distinguish between approval and rejection in a structured format so downstream logic can act predictably on the outcome.
- **FR-010**: The system MUST expose the reflection limit as a configurable value with a default maximum of two additional review cycles.

### Key Entities *(include if feature involves data)*

- **ReasoningStrategy**: The underlying strategy being wrapped by the reflection layer; it represents the base decision-making process.
- **ReflectionConfig**: The configuration that defines the maximum number of reflection attempts and whether the loop is enabled for a given strategy.
- **CritiqueResult**: The structured outcome of the reviewer, containing whether the answer is approved and the feedback explaining any rejection.
- **TraceObservation**: A record from the reasoning trace that provides the evidence against which the critique is evaluated.
- **ReasoningArena**: The operating context in which the strategy runs, including reactive and plan-and-execute scenarios.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: At least 90% of reviewed reasoning tasks reach an approved status within the configured reflection limit.
- **SC-002**: 95% of reflection-enabled workflows emit a trace event showing the critique outcome and the associated decision path.
- **SC-003**: Users and operators can identify when a response was revised because of a critique in at least 99% of recorded cases.
- **SC-004**: The additional reflection work is visible in operational metrics, allowing teams to understand and monitor the cost of review cycles.
- **SC-005**: The system demonstrates a clear improvement in task quality for high-impact reasoning by reducing unsupported or weak conclusions before users or automations act on them.

## Assumptions

- The reflection layer is used only for reasoning quality review rather than for altering the core business rules of the underlying strategy.
- The critic uses the same model family as the base strategy unless a different governance decision is introduced later.
- Trace observations are considered the primary evidence source for critique decisions.
- The default reflection ceiling of two additional passes is sufficient for most operational scenarios but remains configurable for higher-risk workflows.
- Teams are expected to monitor the balance between reasoning quality and additional evaluation cost as adoption grows.
